## 1. システム概要・基本方針

本システムは、日本株・東証上場ETF・米国株を対象とした学習用デモトレードWebアプリケーションである。

- **永続化・データストア:** Cloudflare D1を正規データストアとし、`localStorage` および `sessionStorage` は使用しない。
- **市場データ取得:** 有料株価APIおよびWebSocketは使用しない。HTTPリクエストによる取得を行い、Worker側で **60秒間のレスポンスキャッシュ** を持つ（4.6）。
- **責務分離と負荷削減:**
  - 閲覧用データ成形（パース・DOM描画）はすべてクライアント（ブラウザ）側で行い、WorkerのCPU時間を極小化する。
  - 買付・売却時の取引価格決定および注文の可否・約定判定は、クライアントからの送信価格・時刻を信用せず、Worker側で独立して検証・確定する。
- **資金・資産の整合性管理:**
  - ユーザーの「受渡前・注文中を含めた利用可能資金（買い付け余力）」および「売却可能株数」は Worker 側で **通貨ごとに独立して** 整合性をリアルタイム計算・ロックする（JPYとUSDを混同しない）。
  - 余力チェックと資金ロックは同一 D1 トランザクション（batch）内で完結させ、同時リクエストによる二重使用（TOCTOU）を防止する。
- **注文の約定方式:** 成行・指値ともに **全量約定または不成立（PENDING/EXPIRED/REJECTED）のみ** を扱い、部分約定（一部の株数だけ約定させ残数量を別途保持する処理）は提供しない。
- **空売り:** 保有株数を超える売却注文（空売り）は提供しない。売却可能株数（保有株数 − 既存のPending指値売りロック株数）を超える注文は、成行・指値ともに常に拒否する。
- **金額データの型方針:** 現金残高・ロック額・確定損益などの内部会計値はすべて **INTEGER（最小通貨単位の1/100。JPYなら銭、USDならセント）** で保持し、計算結果の 0.01円/0.01USD 未満の端数は切り捨てる。市場から取得する株価そのもの（`buy_price` 等）は外部データをそのまま保持するため REAL のままとする。
- **移行柔軟性（プロキシ切り替えフラグ）:** 初期構築時は Worker 内プロキシ（CORSヘッダー付与）で動作させ、将来的な独自ドメイン取得後は Cloudflare Rules（Transform/Response Header Modification Rules）へフラグ1つでプロキシ処理を移管し、Workerのリクエスト数をゼロ化できる構成とする。

## 3. データベース仕様 (Cloudflare D1)

### 3.1 テーブル定義

**1. `users`（ユーザーテーブル）**

- `id` (TEXT, PK): ユーザーUUID
- `username` (TEXT, UNIQUE): ユーザー名
- `password_salt` (TEXT): ユーザーごとにランダム生成するソルト値
- `password_hash` (TEXT): パスワードハッシュ（`SHA-256(salt + password)`）
- `role` (TEXT): `'USER'` または `'ADMIN'`
- `status` (TEXT): `'ACTIVE'`（通常）、`'FROZEN'`（凍結）、`'DELETED'`（削除）
- `cash_balance_jpy_c` (INTEGER): 日本円現金残高（単位: 銭 = 1/100円。初期値: 100,000,000 = 1,000,000円）
- `cash_balance_usd_c` (INTEGER): 米ドル現金残高（単位: セント = 1/100USD。初期値: 0）
- `failed_login_attempts` (INTEGER): 連続ログイン失敗回数（初期値 0）
- `lockout_until` (INTEGER): ロックアウト解除時刻（UNIX秒、初期値 NULL）
- `created_at`, `updated_at` (INTEGER): タイムスタンプ

**2. `sessions`（セッションテーブル）**

- `id_hash` (TEXT, PK): Cookieに保持するセッショントークンのハッシュ値
- `user_id` (TEXT, FK, **INDEX**): ユーザーID（凍結・削除時の一括セッション削除を高速化するためインデックスを付与）
- `expires_at` (INTEGER): 有効期限（30日間）
- `created_at` (INTEGER): タイムスタンプ

**3. `symbols`（銘柄辞書テーブル）**

- `code` (TEXT), `market` (TEXT): 複合主キー (`JP` / `US`)
- `symbol` (TEXT, UNIQUE): 外部取得用シンボル（例: `7203.T`, `AAPL`）
- `name` (TEXT), `currency` (TEXT): 銘柄名、通貨 (`JPY` / `USD`)
- `unit_size` (INTEGER): 数量入力UIの増減単位（日本株 = 100、ETF = 1、米国株 = 1）。クライアントの+/-ボタンはこの単位で増減するが、サーバー側はこの倍数であることを強制しない（4.2参照）。
- `active` (INTEGER): 有効フラグ (1: 有効, 0: 無効)

**4. `trades`（保有・売却済み取引テーブル）**

- `id` (TEXT, PK): 取引UUID
- `user_id` (TEXT, FK): ユーザーID
- `code` (TEXT), `symbol` (TEXT), `name` (TEXT), `market` (TEXT)
- `quantity` (INTEGER): 保有株数
- `buy_date` (TEXT), `buy_price` (REAL), `buy_rate` (REAL): 買付時データ（市場価格・為替レートはそのまま保持）
- `status` (TEXT): `'HOLD'`（保有中）または `'SOLD'`（売却済み）
- `sell_date` (TEXT), `sell_price` (REAL), `sell_rate` (REAL): 売却時データ
- `profit_jpy_c` (INTEGER): 確定損益（単位: 銭）。計算式: `(sell_price × quantity × sell_rate) − (buy_price × quantity × buy_rate)` を円換算のうえ銭単位に丸め（0.01円未満切り捨て）。日本株の場合 `buy_rate = sell_rate = 1` とする。

**5. `orders`（注文テーブル）**

- `id` (TEXT, PK): 注文UUID
- `user_id` (TEXT, FK): ユーザーID
- `idempotency_key` (TEXT, UNIQUE): クライアントが注文送信ごとに生成するUUID。二重送信防止に使用（4.2参照）。
- `code` (TEXT), `symbol` (TEXT), `market` (TEXT)
- `order_type` (TEXT): `'BUY_MARKET'`（成行買い）, `'SELL_MARKET'`（成行売り）, `'BUY_LIMIT'`（指値買い）, `'SELL_LIMIT'`（指値売り）
- `target_price` (REAL): 指定指値（成行の場合は NULL）
- `quantity` (INTEGER): 注文株数
- `locked_amount_c` (INTEGER): 注文により拘束・ロックされている相当額（単位: 銭 or セント。`market` カラムにより通貨を判定）
- `ordered_at` (INTEGER), `expires_at` (INTEGER): 有効期限。指値注文はクライアントが「取引所現地時間での日付」（`market = 'JP'` は JST、`market = 'US'` は米国東部時間）を指定し、Worker側でその現地日付の **23:59:59** を UTC の UNIX 秒に変換して保存する。判定に使う OHLC データはそもそも取引時間内の値動きしか含まないため、大引け時刻を厳密に指定しても23:59:59まで含めても実質的な約定判定結果は変わらない。この簡略化により、市場ごとの正確な大引け時刻や祝日・半休日カレンダーを保持する必要がなくなる。指定可能な上限は **注文日から2週間先の日付まで**（下記4.3参照）。成行注文には適用しない。
- `checked_until` (INTEGER)
- `status` (TEXT): `'PENDING'`（未約定指値）, `'EXECUTED'`（約定完了）, `'EXPIRED'`（期限切れ）, `'CANCELLED'`（キャンセル）, `'REJECTED'`（余力不足等による失効）, `'DATA_UNAVAILABLE'`
- `executed_price` (REAL), `executed_at` (INTEGER), `executed_rate` (REAL)

**6. `fx_transactions`（JPY⇔USD 両替履歴テーブル）**

- `id` (TEXT, PK): 両替UUID
- `user_id` (TEXT, FK): ユーザーID
- `direction` (TEXT): `'JPY_TO_USD'` または `'USD_TO_JPY'`
- `source_amount_c` (INTEGER): 両替元通貨での金額（銭 or セント）
- `fx_rate` (REAL): 適用した為替レート（両替実行時に取得、1分キャッシュ対象）
- `result_amount_c` (INTEGER): 両替先通貨での金額（0.01未満切り捨て後）
- `executed_at` (INTEGER): タイムスタンプ

**7. `admin_audit_log`（管理者操作監査ログテーブル）**

- `id` (TEXT, PK): ログUUID
- `admin_user_id` (TEXT, FK): 操作を行った管理者のユーザーID
- `target_user_id` (TEXT, FK): 操作対象のユーザーID
- `action` (TEXT): 操作種別。`'STATUS_CHANGE'`（凍結/解除/抹消）, `'BALANCE_ADJUST'`（残高直接調整）, `'PASSWORD_CHANGE'`（パスワード変更）, `'SYMBOL_UPDATE'`（銘柄辞書更新）
- `before_value` (TEXT): 変更前の値（JSON文字列、例: `{"cash_balance_jpy_c": 100000000}`）
- `after_value` (TEXT): 変更後の値（JSON文字列）
- `created_at` (INTEGER): タイムスタンプ

すべての管理者API（4.5）は、状態変更を伴う操作の実行直後に本テーブルへ1レコードを追記する。ログは追記専用とし、管理画面からの削除・編集手段は提供しない。

## 4. 機能仕様および処理フロー

### 4.1 認証およびアカウント制御

- **ユーザー登録 (Public):**
  1. Turnstile トークンを検証し、不正な場合は即時ブロック（ログイン時と同様のBOT対策を新規登録にも適用）。
  2. クライアント側から自由に登録可能。初期状態は `status = 'ACTIVE'`, `role = 'USER'`。初期デモ資産（`cash_balance_jpy_c = 100,000,000`）を自動付与。
  3. ランダムな `password_salt` を生成し、`SHA-256(salt + password)` を Worker 側で計算して D1 へ保存。
- **ログイン・ブルートフォース対策:**
  1. Turnstile トークンを検証し、不正な場合は即時ブロック。
  2. `lockout_until` が現在時刻より未来の場合は `429 Too Many Requests` を返却。
  3. パスワード誤り時：`failed_login_attempts` を +1。直近5分間に5回失敗で 15分間のロックアウト (`lockout_until` 更新) を適用。
  4. ログイン成功時：失敗カウントとロックアウト時刻をリセットし、`HttpOnly` Cookie を発行。
- **アカウント凍結・抹消時の即時無効化:**
  - 管理者がユーザーを `FROZEN` または `DELETED` に変更した際、`sessions` テーブル（`user_id` インデックス使用）から対象ユーザーの全セッションを即時削除。
- **ログアウト (`POST /api/logout`):**
  - 現在のセッションに対応する `sessions` レコード（`id_hash`）をD1から削除し、Cookieを失効させるレスポンス（`Set-Cookie` で即時期限切れを指定）を返す。
- **パスワード変更（ログイン中のユーザー本人、`POST /api/account/password`）:**
  - ログイン中のユーザーは、**現在のパスワード**と**新しいパスワード**を送信して自分のパスワードを変更できる。Worker側で現在のパスワードを検証（`SHA-256(salt + 現パスワード)` が `password_hash` と一致するか）した上で、新しい `password_salt` を再生成し、新しい `password_hash` を保存する。
  - **パスワードを忘れた場合（ログイン不可な状態）** のリセット手段はユーザー自身には提供しない。この場合は管理者機能（4.5、既存の「パスワードの直接変更」）を通じてのみ変更可能とする。

### 4.2 成行注文・即時判定フロー (`POST /api/orders/market`)

クライアントから現在価格や購入可否判断を送信させず、API側で全自動判定・確定を行う。

1. **リクエスト送信:** クライアントは `code`, `market`, `side` (`BUY` / `SELL`), `quantity`, `idempotency_key`（クライアント生成のUUID）を送信。
   - **二重送信防止:** Worker は `orders.idempotency_key` のUNIQUE制約により、同一キーでの再送信（ダブルクリック・通信リトライ等）を検知する。同一キーが既に存在する場合は新規注文を作成せず、その既存注文の処理結果（`EXECUTED`/`REJECTED`等）をそのまま返す。
   - **数量入力の単位:** クライアントUIの `+`/`-` ボタンは `symbols.unit_size`（日本株=100、ETF=1、米国株=1）単位で `quantity` を増減させるが、テキスト直接入力により `unit_size` の倍数でない任意の数量（例: 日本株を1株単位）も送信可能とする。Worker側は `quantity` が1以上の正の整数であることのみを検証し、`unit_size` の倍数であることは強制しない。
2. **Worker 側でのリアルタイムデータ取得:** Worker が外部市場データへアクセスし、**現在の最新取引価格**および**最新為替レート（米国株の場合）**を取得（4.6のキャッシュを利用）。
3. **購入可能性（余力 / 保有株数）判定（通貨別・単一トランザクション）:**
   - **成行買いの場合:** 必要概算額 ＝ `最新価格 × 数量 × スリッページ許容安全係数（例: 1.05）`（+ 為替換算）。当該通貨の余力（`該当通貨の現金残高 − 同一通貨での既存Pending指値買いロック合計額`）が概算額以上かを、残高チェックと同時に1つのSQL文（`UPDATE ... WHERE 残高 >= 必要額`相当）で検証・仮確保し、他リクエストとの競合を排除する。不足時はエラー (`400 Bad Request: 余力不足`) で即時却下。
   - **成行売りの場合:** 対象銘柄の売却可能株数（`保有株数 − 既存のPending指値売りロック株数`）が指定数量以上か検証。不足する場合はエラーで即時却下。
4. **約定・口座即時更新:** 余力チェック通過後、取得した最新価格を確定約定価格とし、D1の `users`（現金残高更新）および `trades`（保有資産追加/売却更新）を同一トランザクション内で即時更新。実際に引き落とされる金額は最新価格×数量の**実額**のみであり、安全係数（1.05）分の余剰が請求されることはない（成行注文はロック期間を持たないため、返却処理自体が不要）。注文履歴 `orders` にステータス `'EXECUTED'` として保存。

### 4.3 指値注文および買い付け余力・資産ロック仕様 (`POST /api/orders/limit`)

未約定の指値注文による二重使用（オーバーフロー）を防ぐため、注文時に資産をロックする。指値注文も `POST /api/orders/limit` へのリクエストに `idempotency_key`（クライアント生成のUUID）を含め、4.2と同様のUNIQUE制約による二重送信防止を適用する。約定は常に全量のみで、部分約定は行わない（1.参照）。また、`SELL_LIMIT` は売却可能株数を超える注文を常に拒否し、空売りは提供しない（1.参照）。

1. **有効期限（`expires_at`）の指定と検証:**
   - クライアントは指値注文時に有効期限として **「日付」のみ**（時刻は指定不可）を送信する。この日付は当該銘柄の **取引所現地時間**（`market = 'JP'` → 日本時間 / `market = 'US'` → 米国東部時間、サマータイムを考慮）での暦日として扱う。
   - Worker側は、指定日の現地時間 **23:59:59** をUTCのUNIX秒に変換して `expires_at` に保存する。約定判定（4.4）で参照するOHLCデータはそもそも取引時間内の値動きしか持たないため、大引け時刻ちょうどで区切っても現地日付いっぱい（23:59:59）まで含めても判定結果は変わらない。この簡略化により、市場ごとの正確な大引け時刻や祝日・半休日カレンダーの保持は不要とする。
   - **上限チェック:** 指定日は「注文受付時点（Worker側時刻基準）の取引所現地日付」から起算して **最大14日先の日付まで** とする。これを超える指定は `400 Bad Request: 有効期限が上限（2週間）を超えています` として即時却下する。
   - 下限チェック: 指定日が当日（現地日付）より前の場合も同様に却下する。
   - 期限到達後、未約定のまま残っている注文は 4.4 の判定トリガー実行時（または期限超過を検知した任意のアクセス時）に `status = 'EXPIRED'` へ更新し、ロックしていた資金・株数を即時全額解除する。
2. **注文受付と買い付け余力・株数ロック（通貨別）:**
   - **指値買い (`BUY_LIMIT`):** 必要ロック額 ＝ `指定指値 × 数量`（+ 米国株時は適用為替）。当該通貨の有効余力が「必要ロック額」以上かを、判定とロックを同一トランザクションで実行して判定。通過時、`orders` テーブルに `status = 'PENDING'`, `locked_amount_c` = 必要ロック額 で登録。以降の同一通貨での取引計算ではこのロック額を「使用不可資金」として扱う。
   - **指値売り (`SELL_LIMIT`):** 指定数量が売却可能株数以下か判定。通過時、該当する `trades` 内の株数を「ロック状態」とし、成行売りや他注文への二重使用をブロックする。
3. **注文キャンセル (`POST /api/orders/:id/cancel`):** キャンセル実行時、`orders` の status を `'CANCELLED'` に変更し、ロック額・ロック株数を即時全額解除する。

### 4.4 指値の自動遡及判定トリガーと実行

- **トリガー:** 定期的な Cron 実行は行わない。ユーザーのアクセス（ログイン、保有銘柄一覧 `GET /api/portfolio`、注文一覧 `GET /api/orders`）をトリガーにしてバックグラウンドで約定チェックを実行する。
- **判定ロジック (値幅検証):**
  1. `checked_until` から「現在時刻」または「有効期限」までの期間の OHLC チャートを取得（この履歴データは 4.6 の1分キャッシュ対象外）。
  2. 期間内の最安値 (`Low`) および最高値 (`High`) の値幅を検出。
     - **指値買い:** `Low <= target_price` で約定。
     - **指値売り:** `High >= target_price` で約定。
  3. **約定処理・ロック精算・差額返却:**
     - 約定決定時、`orders` を `'EXECUTED'` に更新し、実際の約定価格は `target_price`（指値どおり）とする。
     - ロックしていた資金・株数を正式な資産移動（`cash_balance` の引き落とし・反映および `trades` の確定保存）へ振り替える。
     - **指値買いの場合**、`locked_amount_c` は「指値 × 数量」で確保していたため差額は生じない（指値価格で約定するため）。ただし、遡及判定の対象期間中に約定条件を満たしたが実際にはそれより有利な価格で約定させる運用に変更する場合は、`locked_amount_c − 実約定額` の差額を即時に当該通貨の余力へ返却する。MVPでは指値どおりの価格で約定させるため、通常は差額返却は発生しない想定だが、将来的な仕様変更に備えてこの精算ロジックを共通処理として実装しておく。
  4. **`checked_until` の更新（必須）:** 約定・非約定にかかわらず、判定処理の最後に対象注文の `checked_until` を「今回のチェックで実際に取得した期間の終端時刻」（=処理実行時点の現在時刻）へ必ず更新する。これを怠ると次回アクセス時に同一期間を再取得・再判定してしまい、無駄なAPI呼び出しと二重判定の原因になるため、約定判定ロジックとセットの必須処理として実装する。

### 4.5 管理者機能 (`/admin`)

- **アクセス制御:** すべての管理者用 API (`/api/admin/*`) は、セッションの `role === 'ADMIN'` かつ `status === 'ACTIVE'` を必須検証とする。管理画面フロント（`/admin.html`）はログイン中アプリと同じセッションCookieを利用し、権限がない場合はAPI呼び出し時の`403`を検知してその旨を表示する（管理画面専用のログインは設けない）。
- **提供機能:**
  - ユーザー一覧の閲覧・ステータス変更（凍結 `FROZEN` / 解除 `ACTIVE` / 抹消 `DELETED`）。
  - ユーザーのデモ現金残高（JPY/USD）の直接調整・修正。
  - パスワードの直接変更および Cloudflare Email Routing を用いたパスワード変更通知メールの送信。通知先は`users.email`（任意項目、登録時の必須項目ではない）で、未登録のユーザーには送信をスキップする。
  - 銘柄辞書テーブル (`symbols`) の新規追加・更新・有効/無効切り替え。
  - 任意のユーザーの取引履歴・注文履歴・両替履歴の閲覧（4.7）。
- **監査ログ:** 上記のうちD1への書き込みを伴う操作（ステータス変更・残高調整・パスワード変更・銘柄更新）は、対象データの更新と`admin_audit_log`（3.1）への追記を`db.batch()`で単一トランザクション化する。ただしパスワード変更後のメール送信はD1トランザクションの範囲外（Email Routing側のネットワーク呼び出し）であり、送信の成否に関わらずパスワード変更自体は確定済みとして扱う（送信失敗時はレスポンスでその旨を返す）。

### 4.5.1 管理画面フロントエンドと独立認証

管理画面（`/admin.html` + `/admin.js`, `/admin.css`）は、通常アプリのログインとは**完全に独立したセッション**を持つ。

- **セッション分離:** `admin_sessions`テーブル・`admin_session`Cookie（HttpOnly）・`admin_csrf_token`Cookieを、通常アプリの`sessions`/`session`/`csrf_token`とは別に用意する。管理者アカウント自体は既存の`users`テーブル（`role='ADMIN'`）を引き続き使うが、セッションの発行・検証経路は完全に分ける。管理セッションの有効期限は通常アプリより短い（既定1日）。
- **ログイン方法:** `POST /api/admin-auth/login`（メールアドレス+パスワード、Turnstile必須）、または`POST /api/admin-auth/webauthn/login-options`→`login-verify`（パスキー、WebAuthn）のいずれか。ログイン識別子は`users.username`ではなく`users.email`を使う。
- **パスキー登録:** 既にメール+パスワードでログイン済みの管理者が、管理画面上の「パスキーを登録」から`POST /api/admin-auth/webauthn/register-options`→`register-verify`で自分のブラウザ/端末に紐づく認証器を登録する。1アカウントに複数の認証器（複数端末）を登録できる（`webauthn_credentials`テーブル）。
- **WebAuthn実装方針:** CBORデコード・COSE公開鍵の解釈・署名検証は自前実装すると認証バイパスに直結するリスクがあるため、`@simplewebauthn/server`（Cloudflare Workers対応）に委譲する。チャレンジは`RATE_LIMIT_KV`に短時間（5分）だけ保存し、検証後は使い捨てる。リプレイ対策の署名カウンタ（`webauthn_credentials.counter`）は認証成功のたびに更新する。
- **フロントの画面構成:** モバイル向けのボトムタブUIではなく、PC/タブレットでも扱いやすい一般的な管理画面レイアウト（上部タブ＋テーブル）とする。
  - **ユーザー管理タブ:** 一覧テーブル（ユーザー名・メール・権限・状態・JPY/USD残高）、行ごとに凍結/解除/抹消・残高調整・パスワード変更・履歴閲覧（取引/注文/両替を直近10件まで簡易表示）の操作ボタンを配置。
  - **銘柄管理タブ:** 一覧テーブルと新規追加フォーム、行ごとに有効/無効切り替えボタンを配置。

### 4.6 市場データキャッシュおよび JPY⇔USD 両替機能

- **外部データソース:** Yahoo Finance の非公式 Chart API を利用する。
  - **エンドポイント:** `https://query1.finance.yahoo.com/v8/finance/chart/{symbol}`（プライマリ）。取得失敗時（HTTPエラー、タイムアウト、レスポンス形式不正、`chart.error` が非null等）は、代替として `https://query2.finance.yahoo.com/v8/finance/chart/{symbol}` に同一パラメータで1回リトライする。それでも失敗した場合は取得不可として扱い、下記「非公式APIであることのリスクと対策」の方針（`DATA_UNAVAILABLE`／エラー応答）に従う。プライマリ・代替とも同一の60秒キャッシュポリシーを共有する（片方で取得成功した結果を `symbol` 単位のキャッシュキーに保存し、次回はどちらから取得したかに関わらずキャッシュを優先利用する）。
  - **シンボル形式:** 日本株・東証ETFは `{証券コード}.T`（例: `7203.T`, `1364.T`）、米国株は無サフィックスのティッカー（例: `MSFT`, `AAPL`）。これは `symbols` テーブルの `symbol` カラムにそのまま格納する値と一致させる。
  - **為替レート:** 通貨ペアシンボル `JPY=X`（USD/JPY）を同一エンドポイントで取得する。MVPではUSD/JPYの1ペアのみを扱うため、`symbols` テーブルには含めずWorkerの設定値として固定で保持する。
  - **リクエストパラメータ:** `interval` と `range` をクエリパラメータで指定する。
    - 成行注文・両替時の**現在値取得**: `interval=1m&range=1d` を指定し、レスポンス内の直近の終値（`chart.result[0].indicators.quote[0].close` の末尾非null値、または `chart.result[0].meta.regularMarketPrice`）を最新価格として採用する。
    - 指値の**遡及判定用OHLC取得**（4.4）: `checked_until`〜現在時刻の期間の長さに応じて `interval` を切り替える（例: 当日中〜数日以内なら `interval=5m`、数日〜2週間の範囲なら `interval=1d`）。`range` は判定対象期間をカバーする値を指定する。
  - **CORS制約と取得経路:** Yahoo Finance は CORS ヘッダーを返さないため、ブラウザから直接取得することはできない。したがって本エンドポイントへのアクセスは必ず Worker 経由（5.の `/api/proxy` またはRules移行後の構成）で行う。
  - **非公式APIであることのリスクと対策:** 本APIはYahoo Financeの公式契約に基づくものではなく、予告なく形式変更・アクセス制限がかかる可能性がある。プライマリ・代替（`query2`）の両方が失敗した場合は、6.の方針どおり古い価格で約定させず、該当注文を `DATA_UNAVAILABLE` またはエラー応答とする。過度なリクエスト頻度によるアクセス遮断を避けるため、下記の60秒キャッシュを厳格に適用する。
- **レスポンスキャッシュ:**
  - Worker は外部市場データ（現在値・為替レート）の取得結果を **60秒間** キャッシュする（Cloudflare Cache API または KV を利用、キーは `symbol` 単位）。
  - 成行注文・両替処理はキャッシュされたデータ（60秒以内）を利用してよいが、キャッシュが存在しない・期限切れの場合は必ず外部から再取得する。過去の価格を使い回して古い時刻の相場で約定させることはない（キャッシュ期間内であることが条件）。
  - 指値の遡及判定（4.4）で使用する OHLC 履歴データはこのキャッシュの対象外とし、判定のたびに必要な期間のデータを取得する。
- **JPY⇔USD 両替 (`POST /api/fx/exchange`):**
  1. クライアントは `direction`（`JPY_TO_USD` / `USD_TO_JPY`）と両替元金額を送信。
  2. **不正利用対策:** 本APIはログイン後のセッション（Cookie）を必須とした上で、Cloudflare **Bot Management（Bot Fight Mode）** をゾーンレベルで有効化し、スコアリングによる自動化リクエストの検知・チャレンジ/ブロックを行う。加えてWorker側でも同一ユーザーにつき短時間の連続実行を制限するレート制限（例: 1分間に5回まで）を課し、上限超過時は `429 Too Many Requests` を返却する。Bot Managementはゾーン全体（ログイン・登録・注文・両替すべてのAPI）に適用される汎用の防御レイヤーであり、Worker側のレート制限はユーザー単位のより細かい制御として併用する。
  3. Worker が最新為替レート（60秒キャッシュ利用可）を取得。
  4. 両替元通貨の残高が指定額以上かを検証し、通過した場合のみ同一トランザクション内で両通貨の `cash_balance_*_c` を更新（両替元を減算、両替先を加算）。結果額は 0.01 未満切り捨て。
  5. `fx_transactions` に履歴を記録する。
  6. 両替は即時実行のみとし、指値のような「予約両替」はMVPでは提供しない。

### 4.7 取引・注文・両替履歴の閲覧

取引履歴（`trades`）・注文履歴（`orders`）・両替履歴（`fx_transactions`）はいずれもD1に永続化されており、削除処理は実装しない（キャンセル・期限切れも `status` 更新のみでレコード自体は残す）。閲覧用に以下のAPIを提供する。

- **ユーザー向け（自分自身のデータのみ）:**
  - `GET /api/trades`：自分の保有中（`HOLD`）・売却済み（`SOLD`）取引を一覧取得。`status`, `market`, 期間でのフィルタ、日付降順ページネーションに対応。
  - `GET /api/orders`：自分の注文履歴を全ステータス（`PENDING`/`EXECUTED`/`EXPIRED`/`CANCELLED`/`REJECTED`/`DATA_UNAVAILABLE`）で一覧取得。既存の 4.4（アクセス時の指値遡及判定）のトリガーも本APIの呼び出し時に実行する。
  - `GET /api/fx/transactions`：自分の両替履歴を一覧取得。
  - いずれも他ユーザーのデータへはアクセス不可（`user_id` をセッションから強制的に絞り込み、クエリパラメータでの `user_id` 指定は無視 or 拒否する）。
- **管理者向け（任意のユーザーのデータを閲覧可）:**
  - `GET /api/admin/users/:userId/trades`
  - `GET /api/admin/users/:userId/orders`
  - `GET /api/admin/users/:userId/fx-transactions`
  - いずれも 4.5 のアクセス制御（`role === 'ADMIN'` かつ `status === 'ACTIVE'`）を必須とする。閲覧行為自体は残高やステータスを変更しないため `admin_audit_log` への記録は不要とするが、将来的に不正調査目的でアクセスログを残したい場合は別途 `admin_access_log` を検討する（MVPでは対象外）。

### 4.8 ライブ株価表示（表示専用、WSSに統一）

保有銘柄・注文画面・ヘッダーの現在値表示をリアルタイムに近い形にするため、Yahoo Financeの非公式ストリーミングエンドポイント（`wss://streamer.finance.yahoo.com/?version=2`）をWorker経由で中継する。表示用の現在値取得はこのWSS経路に統一し、HTTPポーリング・HTTPスナップショットは用いない。

- **用途の限定:** 本機能はあくまで**表示専用**であり、成行・指値の約定判定や余力計算には一切使用しない。それらは引き続き4.2〜4.4のとおり、Worker側でのHTTP取得（Yahoo Finance Chart API、60秒キャッシュ、`query1`/`query2`フォールバック）のみを正とする。
- **接続方式（パススルー中継）:** クライアントは自ドメインの `wss://<自分のドメイン>/api/live-prices` にのみ接続する。Workerがこの接続を受け、`fetch()`でYahoo Finance側へ上流接続を張り、双方向にメッセージをそのまま中継する。1クライアント接続につき1本の上流接続を張るだけの単純な中継であり、複数クライアント間で1本の上流接続を共有するわけではないため、Durable Objects等の常時接続インフラは不要。クライアント側はYahoo Financeのドメインを直接知る必要がなく、CSPも`connect-src 'self'`のみで済む。上流への接続には、ブラウザのfetchと異なりOriginヘッダーを明示的に指定でき（本家ブラウザクライアントと同じ`https://finance.yahoo.com`を付与）、User-Agentはクライアントが送ってきたものをそのままパススルーする。
- **データ形式:** サーバーから送られるメッセージはJSON（`{"message": "<base64>"}`）で、base64部分は非公開のprotobufスキーマ（`PricingData`、フィールド1=銘柄ID文字列、フィールド2=価格float32、以降のフィールドは本機能では未使用）。クライアント側では必要な2フィールドのみを読み取る最小限の手書きデコーダを実装し、protobufライブラリは導入しない。
- **可用性:** 非公式・無保証のエンドポイントであるため、接続失敗・切断は当然に起こり得るものとして扱う。上流に繋がらない場合、Workerはエラーで落とさずクライアント側の接続をクローズするのみとし、クライアント側は指数バックオフで再接続を試みつつ、再接続できない間は「読み込み中」のまま静的表示に留める（HTTPフォールバックは持たない。アプリの他機能には影響しない）。
- **マーケットティッカーバー:** ヘッダー直下に、USD/JPY・日経平均(`^N225`)・NYダウ(`^DJI`)の3値を全画面共通で常時表示する。WSS接続確立後、最初のtick受信で表示される（HTTPスナップショットは持たない）。
- **注文画面のライブ価格プレビュー:** 銘柄コード入力時、選択中銘柄の現在値をWSS経由でリアルタイム表示する。あくまで参考表示であり、実際の約定価格は発注時にWorkerが取得する価格（成行）または指値どおりの価格（指値）で確定する。

### 4.9 米国株の円貨決済（買いのみ）

米国株の買い注文（成行・指値）に限り、決済通貨として日本円（円貨決済）を選択できる。売却時の受取通貨選択、および日本株での使用は対象外（常に銘柄本来の通貨）。

- **買い付け余力の参照先:** 円貨決済を選択した場合、余力チェック・資金ロックはUSD残高ではなくJPY残高を参照する。それ以外（外貨決済・日本株）は従来通り。
- **成行買い（円貨決済）:** 発注時点でWorkerが取得した最新価格・最新為替レートを用い、円換算額（`価格 × 数量 × 為替レート × スリッページ安全係数`）でJPY余力を検証・仮確保する。実額確定後、安全係数分の差額は即座にJPYへ返却する（4.2の成行注文と同じ精算パターン）。
- **指値買い（円貨決済）:** 「指値どおりの価格で約定する」という4.4の原則にならい、為替レートも**注文時点のレートで円換算額を確定・固定**し、`locked_amount_c`としてJPYをロックする。約定時点のレートでの再計算は行わない（為替変動リスクの評価はMVPでは省略する簡略化）。
- **不成立時の返金:** 円貨決済の指値注文がキャンセル・期限切れとなった場合、ロックしていた金額はJPYのままそのまま全額返却する（換算のやり直しは発生しない）。
- **売却:** 円貨決済で購入した米国株も、保有株数・売却フローは通常の米国株と同一（`trades`テーブル上は区別しない）。売却時の受取は常にUSDで、円貨受取（決済通貨選択）には対応しない。

### 4.10 銘柄マスタ(`symbols`)の自動同期

毎日 **08:30（JST）＝ 23:30（UTC）** に Cloudflare Workers の **Cronトリガー**（`wrangler.json`の`triggers.crons`）で銘柄マスタを自動更新する。

- **データソース:**
  - **日本株:** 東証（JPX）が自ら公開している上場会社一覧（`data_j.xlsx`）。J-Quants APIも検討したが、利用規約上「取得データを閲覧可能な形式で配布・共有することを禁止」する条項があり、複数人が利用しうる本アプリでは規約抵触リスクがあると判断し、JPXの公開ファイルに切り替えた。
  - **米国株:** SEC（米証券取引委員会）が公開する `company_tickers.json`。米国政府の公開データであり配布制限はないが、SECのフェアユースポリシーに従い、取得時のリクエストには必ず`User-Agent`（連絡先を含む）を明示する。
- **xlsx解析:** `data_j.xlsx`はZIP+XML形式のExcelファイルであり、Worker上で直接パースするために `xlsx`（SheetJS）ライブラリを使用する。Cloudflare Workersの`nodejs_compat`互換フラグ（`Buffer`等の提供）を有効化して動作させる。列名（「コード」「銘柄名」「市場・商品区分」）はJPX側の書式変更で変わりうるため、想定外の列構成を検知した場合はエラーとして扱い、サイレントに壊れたデータを取り込まない。
- **取り込み範囲:** 日本株は「市場・商品区分」に「内国株式」を含む行のみを対象とし、ETF・REIT・外国株等はこのファイルからは取り込まない（単元は一律100株として登録。2018年の単元株統一後はほぼ全銘柄が該当するための簡略化）。米国株はSECファイルの全ティッカーを対象とする（単元は1株）。実データ検証の結果、対象3,707件は重複なし。2024年以降TSEが新規上場銘柄向けに導入した英数字混在コード（例: `130A`）も存在するため、`symbols.code`はINTEGERではなくTEXT型としている（Yahoo Finance側のREST APIでの対応も確認済み）。
- **反映方法:** 取得した一覧を`symbols`テーブルへ `INSERT ... ON CONFLICT(code, market) DO UPDATE` でUPSERTする。D1の`batch()`は1呼び出しあたりの文数に実務上の上限があるため、50件ずつチャンク分割して順次実行する。日本株・米国株いずれか一方の取得に失敗しても、成功した方は反映したうえでエラー内容を返す（部分的な失敗で同期処理全体を止めない）。
- **配信キャッシュ（12時間）:** `GET /api/symbols`（クエリなし・全件取得のケースのみ）は、Workers KV（`RATE_LIMIT_KV`）に**12時間**キャッシュしてから配信する。検索クエリ付き（`?q=...`）のリクエストは都度D1へ直接問い合わせる。銘柄同期が実行されるたびに、このキャッシュは即座に無効化され、次回アクセス時にD1から再構築される。
- **手動同期:** Cronの実行を待たずに `POST /api/admin/symbols/sync`（管理画面の「🔄 JPX/SECから自動同期」ボタン）で即時実行できる。

## 5. API プロキシ・CORS 切り替え仕様

Workers のリクエスト制限を回避するため、以下の 2 段階の切り替え構成を実装する。

- **切り替えフラグ:** `wrangler.json` 内の環境変数 `USE_WORKER_PROXY` (`"true"` / `"false"`)
- **挙動:**
  - `USE_WORKER_PROXY = "true"`（初期状態）: `/api/proxy?url=...` へのリクエストに対し、Worker が外部 API からレスポンスを取得し（60秒キャッシュ経由）、CORS ヘッダー（`Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials: true`）を付与して返却する。
  - `USE_WORKER_PROXY = "false"`（独自ドメイン取得後・Rules 移行時）: API プロキシへのアクセスは `404` を返し、クライアントは外部 API または専用ドメイン宛てに直接リクエストを送信する。CORS ヘッダーの書き換えは Cloudflare の **Response Header Modification Rules**（インフラ層）が担うため、Worker の実行回数および CPU 時間は消費されない。

## 6. エラーハンドリング・セキュリティ要件

- **データ非整合時の動作:** 外部データが取得できない場合、過去の価格で売買・約定させず、注文受付や処理をエラー（または一時保留）とする。
- **安全対策:**
  - すべての SQL 実行においてバインド変数を使用し、SQL インジェクションを防止する。
  - CSV エクスポート時、先頭文字が `=`, `+`, `-`, `@` で始まるセルに対して数式インジェクション対策を施す。
  - 認証が必要な API レスポンスには `Cache-Control: no-store` を設定する。
  - 状態変更を伴う API（注文・両替・キャンセル・管理者操作等）は `SameSite=Lax` Cookie に加えて **CSRFトークン** の検証を必須とする。
  - パスワードは `password_salt`（ユーザー毎ランダム値）と `SHA-256` で保護する。将来的な強化としては PBKDF2 / bcrypt / scrypt 等のストレッチング付きハッシュへの移行を推奨する。
  - **Cloudflare Bot Management（Bot Fight Mode）** をゾーンレベルで有効化し、本システムの全APIエンドポイント（`/api/*`）への自動化リクエストをスコアリング・ブロックする。ログイン・新規登録の Turnstile、両替APIのユーザー単位レート制限（4.6）と多層的に併用する。**注意点:** Bot Management はあくまで「外部からこのシステムへ入ってくるリクエスト」を守るものであり、Worker が Yahoo Finance へアクセスする際の取得方式（4.6）には影響しない。Yahoo Finance側のアクセス遮断リスクへの対策は、4.6に記載の60秒キャッシュの厳格運用で行う。

v0.1.0（GitHub Release）リリース後に報告された不具合・追加要望を整理する。本節は**仕様の計画のみ**であり、実装はこれから行う。

### 7.1 認証まわりの不具合・改善

- **7.1.1 Turnstileウィジェットが画面遷移で消える（不具合）**
  原因: ログイン⇔登録の切り替え時に`innerHTML`で画面全体を再構築しており、Turnstileの`cf-turnstile`要素も一緒に作り直されるが、Turnstile側は最初の1回しか自動レンダリングしないため、2回目以降は空のまま表示される。
  対応: `turnstile.render(container, {sitekey, callback})`による**明示的レンダリング**に切り替える。画面を離れる際は`turnstile.remove(widgetId)`で確実に破棄し、再表示のたびに再レンダリングする。

- **7.1.2 新規登録: パスワード確認入力**
  「パスワード」に加えて「パスワード（確認）」欄を追加し、一致しない場合はクライアント側で送信をブロックしてエラー表示する（サーバー側のバリデーションは不要、UI改善のみ）。

- **7.1.3 新規登録と同時にログイン完了**
  現状: `POST /api/register`は作成のみでセッションを発行せず、ユーザーは登録後に改めてログイン画面でログインし直す必要がある。
  対応: `POST /api/register`の成功時、`POST /api/login`と同様に`session`/`csrf_token`Cookieをその場で発行する（Turnstile検証は登録時に既に行っているため、二重検証は不要）。フロントは登録成功後、追加のログイン操作なしでそのままアプリ画面へ遷移する。

- **7.1.4 アカウント削除（ユーザー自身）**
  設定タブに「アカウント削除」ボタンを追加する。押下時に確認ダイアログ（「本当に削除しますか？この操作は取り消せません」等）を表示し、確認後に新規エンドポイント`POST /api/account/delete`（要CSRF・要ログイン）を呼び出す。管理者による抹消（4.5の`DELETED`ステータス変更）と同じ扱いとし、`status='DELETED'`に更新のうえ`sessions`から全セッションを削除する。保有株・取引履歴は監査目的で保持し、物理削除はしない（既存の抹消ユーザーの扱いと同様）。

### 7.2 UI/UXの全般的な改善

- **7.2.1 レスポンシブ対応**
  現状、`public/styles.css`は`#app { max-width: 480px; margin: 0 auto; }`でモバイル固定幅になっており、PC/タブレットで開いても中央に細長いモバイルUIが表示されてしまう。
  対応: `@media (min-width: 768px)`等のブレークポイントを追加し、広い画面では
  - ボトムタブバーではなく左サイドナビゲーション、または上部タブに切り替える
  - コンテンツ幅を画面に応じて拡張し、余白を活かしたレイアウト（例: ホーム画面は2カラムでポートフォリオと明細を並べる）
  に変更する。管理画面（`admin.html`）は元々PC向けレイアウトのため対象外。

- **7.2.2 指値有効期限のカスタムUI**
  ネイティブの`<input type="date">`をやめ、カレンダーUIを自前で実装する（既存の`btn`/`card`デザインに合わせた見た目）。

- **7.2.3 成行注文で指値欄が表示される不具合**

### 7.3 銘柄検索・パフォーマンス

- **7.3.1 注文画面の銘柄プルダウンをサーバー側検索方式に変更**

- **7.3.2 銘柄検索画面の新設**
  注文とは独立した「銘柄検索」画面（新タブまたはホームからの導線）を追加する。
  - 日本株・米国株どちらも、銘柄名・ティッカーシンボル・証券コードのいずれでも検索できる（既存の`GET /api/symbols?q=...`がcode/name/symbolのLIKE検索に対応済みのため、バックエンド変更は不要）。
  - 検索結果には現在値をライブ表示する（既存の`/api/live-prices`WSSパススルーへ検索結果分の銘柄を動的にsubscribeする）。

### 7.4 マイページ（新規画面）

保有資産の推移を確認できる新画面「マイページ」を追加する。

- **表示項目:**
  - 現金残高の推移（JPY/USD）
  - 評価額の推移（保有株式の時価評価額）
  - 総資産の推移（現金+評価額の合計、円換算）
  - 総資産額（現在値、リアルタイム）
  - 評価損益（保有中の取引の含み損益合計、現在値ベース）
- **推移データの取得方法:** 新規テーブル`asset_snapshots`に、**日次（1日1回）**のスナップショットを記録する。既存のCronトリガー（4.10、毎日08:30 JST実行）に同居させ、銘柄マスタ同期と同じタイミングで全ユーザー分のスナップショットを取る。
  ```sql
  CREATE TABLE asset_snapshots (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL REFERENCES users(id),
    snapshot_date TEXT NOT NULL, -- YYYY-MM-DD（JST基準）
    cash_jpy_c INTEGER NOT NULL,
    cash_usd_c INTEGER NOT NULL,
    valuation_jpy_c INTEGER NOT NULL, -- 保有株式の時価評価額（円換算）
    total_assets_jpy_c INTEGER NOT NULL, -- 現金+評価額の合計（円換算）
    created_at INTEGER NOT NULL
  );
  CREATE UNIQUE INDEX idx_asset_snapshots_user_date ON asset_snapshots(user_id, snapshot_date);
  ```
  日次スナップショットのため、当日分の「現在の総資産額」「評価損益」はスナップショットからではなく、その場でHTTP取得した現在値（4.2の成行注文と同じYahoo Finance Chart API、60秒キャッシュ）を使ってリアルタイムに計算する。過去分のグラフ表示のみ`asset_snapshots`を参照する。

### 7.5 現金増額申請（要承認）

ユーザーが運営（管理者）に対してデモ用現金残高の増額を申請し、管理者が承認/却下する機能を追加する。

- **新規テーブル:**
  ```sql
  CREATE TABLE cash_topup_requests (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL REFERENCES users(id),
    currency TEXT NOT NULL CHECK (currency IN ('JPY', 'USD')),
    amount_c INTEGER NOT NULL,
    reason TEXT, -- 申請理由・メモ（任意入力）
    status TEXT NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'APPROVED', 'REJECTED')),
    requested_at INTEGER NOT NULL,
    decided_at INTEGER,
    decided_by TEXT REFERENCES users(id) -- 承認/却下した管理者
  );
  CREATE INDEX idx_cash_topup_requests_user ON cash_topup_requests(user_id);
  CREATE INDEX idx_cash_topup_requests_status ON cash_topup_requests(status);
  ```
- **申請（ユーザー側）:** マイページまたは設定から、金額・通貨・理由（任意のメモ欄）を入力して`POST /api/cash-topup-requests`を呼ぶ。ステータスは`PENDING`。
- **承認/却下（管理画面）:** 管理画面に新しいタブまたはユーザー管理内のセクションとして、`PENDING`な申請の一覧を表示し、承認（`PATCH /api/admin/cash-topup-requests/:id`、`status: APPROVED`）すると、対象ユーザーの該当通貨残高へ即座に加算する。却下時は残高変更なし。承認・却下いずれも`admin_audit_log`へ記録する。
- **履歴への反映:** 「運営からの入金」は、`trades`テーブル（株式保有専用のスキーマ）には混ぜ込まず、既存の「履歴」画面（4.7、現在は注文/取引/両替のサブタブ）に**「入出金」サブタブを追加**し、承認済み（`APPROVED`）の`cash_topup_requests`をそこに表示する形で対応する。
